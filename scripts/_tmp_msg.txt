0.3.5：修掉「从界面点下载，906MB 白下」——0.3.4 那次修复漏了一半

用户实测撞到的：跑完整版（不带语义层），从界面「设置」页点「下载语义层权重」，
老实下完 906MB，开语义层才看到 No module named 'torch'。906MB 白下。

根因是同一件事有两份实现，各漏一半：

  CLI fetch-decision    0.3.4 补了构建能力检查 + 落盘路径   -> 修好了
  界面「设置」页按钮     两样都没有                          -> 没修到

而且界面那份的落盘还在用 self._onnx_dir.get() 的**原始相对字符串**去 mkdir
——那是相对当前工作目录，和 CLI 里 0.3.4 已修过的是同一个缺陷。
修了一处、验证过了、另一处还在，是最难查的那类缺陷。

修法：把判断抽成 decision.preflight_fetch()，CLI 与界面共用。它一次做完
三件事——已就绪就短路、构建加载不了就拒绝、落盘绝不返回相对路径。
返回 FetchPlan，两边按各自的界面形式呈现：

  CLI：打印 + input() 询问，--force 跳过
  界面：直接拒绝，不弹对话框（点按钮就该是有效动作，
        弹"要不要继续"然后照样下 906MB 算不上保护）

判据用 available() 的返回语，不靠猜：以「缺少」开头的是权重文件不在
（下载能解决），其余都是这个构建缺依赖（下载解决不了）。

顺带改准一句文案：available() 看不出自己在哪个变体里跑，原来写死"这个精简版
exe"，完整版报这句会让用户以为下错了包。改成"这个 exe 没带语义层……
打包版里只有 semantic 变体带语义层"。

测试里踩到的两件事也一并记进版本说明：
  * EventBus.close() 把 _closed 永久置真，而 app fixture 每次 teardown 都
    close 那条 module 级总线，于是同文件里只有第一个测试能收到 sink 派发
    ——表现为"单跑通过、一起跑必挂"。改用轮询 bus.since()，也正是界面的用法。
  * 一条 preflight 测试原本"碰巧通过"：本仓库真实存在 models/laya-onnx/
    multilingual，兜底第一条就命中，压根没走到内嵌分支。现已把解析结果钉死。
  * 界面 fixture 提到 conftest.py，两个 UI 测试文件共用一份 Tcl 解释器。

单测 1106 通过（新增 12），三个产物均 0.3.5，真包实测：完整版回答 n 后
没建目录、一个字节没下；语义版仍报「无需下载（打包内嵌）」。
