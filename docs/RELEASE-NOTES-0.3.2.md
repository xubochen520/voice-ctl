# voice-ctl 0.3.2：按住说话不再吃掉开头

按住快捷键说话 → **本地离线**识别 → 理解整句话 → 执行。全程不联网、零调用成本。

这一版只修一件事，但它是"能不能用"级别的事：**按住热键说的头一个字，以前会被吃掉。**

## 问题是什么

日志里长这样：

```
15:51:41 INFO  [session] ● 录音中 …
15:51:42 DEBUG [session] 录音 210ms 峰值 0.040，排队识别
15:51:42 ERROR [outcome] 听到  : "嗯"
    命中  : schedule  via matcher (score=0.83 scored alias='闹钟')
    执行  : ✗ 没听出时间
```

按住 `alt+space` 明明说了好几秒，录下来的却只有 210ms，识别出来一个「嗯」，
然后它还以为你在说日程。看着像识别不准，其实是**录音链路根本没接到**。

## 三个真正的原因

**一、开流太慢，而它是在按下之后才开始的。**

实测冷开流要 **319ms**：

```
=== B. Recorder 开流耗时 ===
  冷启动 start(): 319ms（首帧在路上，这段说话会丢）
```

热键按下 → 才开始建音频流 → 319ms 后才真的在采。你按下就开口，这 319ms 说的话
根本没有麦克风在听。三个字能吃掉一个：「明天八点」进去变成「天八点」。

代码里其实**早就写好了预热机制**（`Recorder.arm()` / 环形预滚缓冲），注释里还
把它为什么存在写得很清楚。但它从来没被接上——`HotkeyListener` 提供了
`on_arm` / `on_disarm` 两个回调，`runner.py` 一个都没传。于是一个字没少地
烂在那里，没被任何人调用过。

**二、开流压在键盘钩子线程上，威胁到热键本身。**

`press()` 是在 pynput 的**低级键盘钩子回调**里跑的。Windows 给钩子 300ms 预算，
超了会**悄悄摘掉钩子**——症状是"按几次之后热键忽然没反应"，重启才好，而且日志上
什么都看不到。319ms 正好越线。所以修法不是"提前开流"这么简单：开流无论如何都
不能在钩子线程里做。

**三、"手快"路径会静默丢录音。**

修的过程中撞出一个更隐蔽的：松开比开流快时，录音会**凭空消失**——不报错、不交付，
日志上只有"录音中"没有下文。原因是 `release()` 和开流线程分两次读同一组状态，
丢了更新：release 先把 `_recording` 置 False 并把 `capturing` 读成 False 提前返回，
开流线程随后才把 `capturing` 置 True，于是没有任何一方去收尾。

这不是理论风险，它就在那份日志里：**4 次「● 录音中」，只有 1 次走到「松开，正在识别」。**
另外 3 次按了、说了、什么都没有发生，连一行错误都没有。

## 改了什么

| | 改动前 | 改动后 |
|---|---|---|
| 开流时机 | 按下主键才开始（319ms） | **按下修饰键就开始**（`on_arm` 接上了） |
| 开流在哪跑 | 键盘钩子线程（319ms，逼近 300ms 红线） | 后台线程（钩子回调约 0ms） |
| 预滚缓冲 | 被清空 | **保留**，开流期间的音频当开头交出去 |
| 时长基准 | 流开好的时刻 | **按下热键的时刻** |
| 松手早于开流完成 | 静默丢录音 | 照常交付 |
| 界面反馈 | 按住时什么都不显示 | **"● 正在录音 1.2s" + 电平条** |

## 实测（这台机器，i7-13650HX）

合成按住 `alt+space` 两秒，各跑三遍，数字完全一致：

| | 改动前 | 改动后 |
|---|---|---|
| **按下 → 真的在采** | **317ms**（三次：317 / 315 / 325） | **0ms** |
| 按住 2 秒录到多少音频 | 1664ms | **2106ms** |
| 预滚 | 0ms | 104ms |

同一句 2 秒的话，多拿回 **442ms** 的音频——正好是"开头半个字被截掉"的量级。

**为什么不丢字**：预滚缓冲保留了开流那段时间进来的音频，`start()` 把它当成开头。
所以哪怕热键是单键（`<f9>`，没有"修饰键提前量"可用）也不会丢字，只是延迟由
319ms 变成"后台 319ms"，音频本身一个字不少。

## 为什么之前一直没被发现

- **听起来像识别问题**：「嗯」被识别得清清楚楚，模型没做错事。
- **手测撞不到**：只有在"按下就开口"时才会丢，慢条斯理地说反而没事。
- **失败时机随机**：松开早于开流完成的那条路径要拼手速，得对着日志一行行看才
  看得出录音少了。

## 顺带修的

- **单键热键 `<f9>` / `<tab>` 也能用**：以前这类热键没有"修饰键按下"这个提前量，
  冷开流的 319ms 必然发生。现在音频一定会被保留。
- **`max_duration_ms` 超时收尾时，提示音不再被录进去**：录音结束的提示音原本在
  关流之前播，会被算进这次录音的尾巴里。现在先关流再响。
- **录音指示**：以前按住热键那几秒界面上毫无反应，用户不知道到底在不在录，只能
  反复点「启动监听」——日志里那串「已启动 / 已停止」就是这么来的。
- **停止监听时会关掉麦克风**：以前只 abort 会话、不关录音器。预热状态下（修饰键
  按着、主键还没按）流是开着的，停止监听之后 Windows 的麦克风图标还亮着。

## 一个被说错很久的事：语义层离不开 torch

翻日志时看到用户开了 `[decision]` 语义层、还下了 873MB 权重，但每次启动都是：

```
WARN [decision] 语义层启用失败，已回落到仅别名匹配：
     没装 laya 或版本不对（No module named 'torch'）。装法：pip install "laya[onnx]"
```

**这条报错是误导的**：`laya[onnx]` 早就装好了，权重也下齐了（873MB 就在
`models/laya-onnx/multilingual/`），问题是**这个 exe 里没有 torch**。

而且"用 ONNX 权重就不需要 torch"这个说法本身就是错的，我把它从代码注释里改了：

```
File "laya\onnx_agent.py", line 15, in <module>
    from laya.common import (...)
File "laya\common.py", line 13, in <module>
    import torch
ModuleNotFoundError: No module named 'torch'
```

`laya.onnx_agent` 顶层 import `laya.common`，而 `laya.common` 第一行就
`import torch`，单文件里 40 多处直接用 `torch.nn` / `torch.softmax` /
`torch.device("meta")`。**torch 是硬依赖，跟权重格式无关**（实测 502MB，
外加 transformers 100MB）。

打包时这就成了一个选择题。0.3.2 加了 `VOICE_CTL_BUNDLE_DECISION=1`，实测三种产物：

| 变体 | 体积 | `--version` 启动 | 语义层 | 打包开关 |
|---|---|---|---|---|
| 精简版 | 84MB | 4.6s | ✗ | （默认） |
| 完整版 | 236MB | 4.3s | ✗ | `BUNDLE_MODEL` + `BUNDLE_LLAMA` |
| 全量版 | **902MB**（目录版） | **0.3s** | ✓ | 再加 `BUNDLE_DECISION` |

**全量版默认出目录版（onedir），不是单文件。** 这是实测逼出来的：单文件 exe 每次
启动都要把内嵌数据解到临时目录，600MB 的 torch 让 `--version` 从 4.3s 变成
**20.8s**——一个语音工具启动要 21 秒，等于不能用。目录版文件就在 exe 旁边，
启动 0.3s。要单文件仍可显式 `VOICE_CTL_ONE_FILE=1`，但请先想清楚那 21 秒。

顺带修掉一个打包缺陷：spec 里原本把 `laya.calibrate` 当"可选依赖"排除了，
但 `laya/onnx_agent.py` 第 220 行和第 652 行都在函数体里 `from .calibrate import`。
表现为 exe 启动 20 秒之后报「加载 ONNX 失败：`No module named 'laya.calibrate'`」
——报错指向权重，真因在打包配置里。开语义层时现在不排除 laya 的任何子模块。

默认仍然是**不带语义层**：它是可选的第 1 层，而 0.5GB 的 torch 不该让所有人买单。
但错误提示改了——现在会说清是"这个 exe 没带语义层、装 pip 包修不了、要重打包"，
而不是让人去装一个早就装好的包。

## 升级注意

- 不需要改配置，行为向后兼容。
- 带修饰键的热键（默认 `ctrl+alt+space`）现在会在你按下 Ctrl/Alt 的那一刻把
  麦克风打开约 150ms 后进入待命。这是提前量，不是偷录：松手即关流，修饰键按住
  不放超过 3 秒也会自动关掉。
- 单键热键（`<f9>` 等）没有这个提前量，麦克风只在录音时打开。

## 实测汇总

| 项 | 实测 |
|---|---|
| 冷开流 | 319ms（预热后 0ms） |
| 按下 → 真的在采 | 317ms → **0ms** |
| 按住 2 秒录到的音频 | 1664ms → 2106ms |
| 修的缺陷 | 开头 319ms 音频被丢、手快时录音静默消失 |
| 单测 | **982 个，约 64 秒** |
